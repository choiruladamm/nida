# Live schedule panels

Issue: #7. Menu bar and notch host the same `ScheduleView` and the same `PrayerDataStore` instance owned by `NotchPanelController`. Settings reads that instance too. No provider logic or schedule copies live in the views.

The panel displays city-local date, five prayer times, next-prayer highlight and countdown, elapsed styling, and source/time zone. The pure timeline supplies exact prayer and midnight boundaries; A shared native TimelineSchedule anchors its first entry to the requested current instant, then updates the rows there while the system timer renders the countdown. After Isya, tomorrow's Subuh appears only with exact next-day coverage. A missing next day is stated explicitly.

Opening either view restores/refreshes coverage. The store guards simultaneous loads and the repository coalesces requests and reuses today's cache. Date changes reload current/next-month coverage; wake refreshes it. Refresh does not erase valid rows; failures appear beside retained data. Without today's coverage, no old timetable is substituted. City choice is reachable through Settings; refresh is inline and Quit remains in the menu bar.

The owner-accepted notch redesign is specified in [DESIGN.md](../DESIGN.md): a 384 pt wide black/glass panel, measured camera wings, city/next-prayer hierarchy and a horizontal strip of all five prayers. The menu retains vertical rows. Both surfaces fit natural content; neither has an internal schedule scroll viewport. Refresh messages wrap to three lines above the source/actions instead of taking space away from prayer cells. The notch silhouette and pointer bounds use the measured rendered height; old 364/52 pt geometry budgets are only startup fallbacks.

The schedule opens after 180 ms hover on the collapsed camera trigger. A hover-opened schedule closes 250 ms after pointer exit; clicking pins it for explicit interaction, with Escape/outside dismissal. A calendar/date header replaces the old close button. Settings closes the originating surface before opening. Display names such as Jakarta Selatan are separate from the provider city used for schedule requests.
Verification: `make test` exercises shared store ownership, concurrent restoration without extra provider calls, pure next-day/midnight/expiry coverage, offline recovery, and native content fit. `make smoke` checks real panel geometry and focus. Keyboard/VoiceOver, arbitrary-background glass readability, midnight on a running Mac, fullscreen, and external displays require hardware review; automated fit checks are not visual approval.

Regression: passing only future dates to an explicit schedule initially rendered the upcoming prayer boundary as the current instant, advancing the next prayer early. Both panels and Settings now use PrayerDisplaySchedule, which emits the requested current instant first. A regression test verifies 11:00 → Dzuhur with 40 minutes remaining, then 11:40 → Ashar.

Historical refresh-overflow regression: a previous scroll-based layout allowed error copy to overlap the footer. The accepted layout removes that viewport, fits the panel to content and retains bounded error text with full help. Refresh coalescing/rate-limit regression coverage still checks that repeated actions preserve cached data and add only one in-flight request. Earlier captures/test results establish their original revisions; see [current verification](mvp-verification.md) for the revamp.
